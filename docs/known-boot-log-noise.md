# Known benign boot-log noise

An itera host boots to a healthy state (`systemctl is-system-running` → `running`,
`systemctl --failed` → 0 units), but the journal still carries a recurring set of
`err`/`warning` lines on every boot. They are all non-fatal. This is the triage
reference so they don't get re-investigated each time — the noise itera could fix
has been fixed; what remains is upstream or hardware-specific and is documented
here on purpose.

To pull the errors for the current boot (filtering the dbus-broker spam):

```
journalctl -b 0 -p err --no-pager | grep -v "Ignoring duplicate name"
```

## Accepted — upstream (nix-mineral / nixpkgs / systemd)

See the comment block in `modules/nixos/core/hardening.nix` for the toggle points.

- **`udev-worker: Error running install command '/usr/bin/disabled-*-by-security-misc' … retcode 127`** (thunderbolt, intel_wmi_thunderbolt, pmt_class). Kicksecure's `nm-module-blacklist.conf` disables modules via a `/usr/bin/…` path absent on NixOS. It fails **closed** (the module never loads), so hardening intent is intact; only the log line is cosmetic. Toggle: `nix-mineral.settings.etc.kicksecure-module-blacklist`. Decision: accept — re-implementing natively via `boot.blacklistedKernelModules` was considered and declined.
- **`jitterentropy.service.d/overrides.conf: Failed to parse LimitMEMLOCK=`.** nixpkgs emits an empty reset line before the real `LimitMEMLOCK=2M` (which applies); systemd warns on the empty one. Report upstream rather than patch locally.
- **`systemd-sysctl: Couldn't write '0' to 'fs/binfmt_misc/status'`.** `nix-mineral.settings.kernel.binfmt-misc = false` writes the sysctl to keep binfmt_misc disabled; the write fails only because the fs isn't mounted, so the intent holds. Do **not** flip the toggle on to silence it — that weakens hardening.
- **`dbus-broker-launch: Ignoring duplicate name …` / `… is not named after the D-Bus name …`** (~120 lines/boot). An aggregation artifact of nixpkgs shipping the same `.service` files in both `/run/current-system/sw/share/dbus-1` and individual package outputs (bluez, NetworkManager, gnome-keyring, tumbler, nemo, gvfs, …), plus upstream tumbler/nemo naming quirks. Not fixable at the itera layer.
- **`accounts-daemon: Unable to open /etc/tcb: No such file or directory`.** Kicksecure/security-misc (via nix-mineral) hardens `login.defs`/pam to expect the tcb-style shadow directory `/etc/tcb`, which NixOS does not create. accounts-daemon probes it once at startup and moves on; cosmetic. No itera-layer fix — originates in the bundled hardening layer.
- **`make-initrd-ng: Warning: Couldn't satisfy dependency libcrypt.so.1 (…) for …libsystemd-shared-260.so`** (during shutdown-ramfs generation). systemd's initrd/shutdown-ramfs dependency resolver in nixpkgs emits spurious "couldn't satisfy" warnings for several libs (libcrypt, and elsewhere glibc/kbd/libgcc/libidn2) under `boot.initrd.systemd`. Non-fatal: the shutdown ramfs still builds and `systemd-shutdown` runs (reboots complete). Known open upstream bug ([nixpkgs#463894](https://github.com/NixOS/nixpkgs/issues/463894), PR [#508087](https://github.com/NixOS/nixpkgs/pull/508087)). Do **not** hand-add `libxcrypt-legacy` to the initrd closure — a fragile shim that wouldn't cover the other warned libs.

## Accepted — session startup races

These fire once, early, because a user-session daemon starts before the thing it
probes exists. Each recovers on its own; the capability works once the system has
settled, so there is nothing to fix.

- **`wireplumber: spa.bluez5: BlueZ system service is not available`.** WirePlumber's bluez5 monitor probes D-Bus at session start; `bluetooth.service` came up ~40 s later. The monitor picks the service up via D-Bus activation once it appears, so Bluetooth audio works — verify with `systemctl status bluetooth` (active) rather than by the log line.
- **`pipewire: spa.alsa: 'hdmi:0': playback open failed: Permission denied`.** This is the **greeter's** PipeWire, not the user's: greetd runs a full user session, so a second PipeWire/WirePlumber pair runs as `greeter` and holds the ALSA cards. At the moment the user logs in, logind moves the `/dev/snd/*` seat ACL to the new session and the greeter's instance loses access, logs this, and exits. The user's own PipeWire is unaffected — check `wpctl status` for the sink.

  **This line does not explain missing audio devices after login.** If sinks/sources are absent for tens of seconds into a session, the card had not registered yet — that is a kernel-side probe question, not a PipeWire one.

  Measure it correctly. **`usbcore: registered new interface driver snd-usb-audio` is the time the _module loaded_, not the time the _card appeared_** — if the module is force-loaded early it prints early even when the card is still a minute away, which makes it useless as a readiness signal. Use the card node instead: `ls -l --time-style=full-iso /dev/snd/controlC*` on the running system, or watch `/proc/asound/cards`. Compare that against session start (`systemctl --user show -p ActiveEnterTimestamp wireplumber`); the difference is the window with no audio.

  Two distinct causes, which need different fixes:
  - **Slow probe.** `parse_audio_format_rates_v2v3(): unable to retrieve number of sample rates` / `cannot get freq (v2/v3): err -110` means the device is not answering UAC2 clock queries and the probe is burning ~5 s per timeout. Force-loading the module early (`itera.hardware.kernelModules = [ "snd_usb_audio" ]`) so it is resident before the device enumerates avoids this on some hardware — but it removes those errors without necessarily making the card appear sooner, so re-measure with the card node before calling it fixed.
  - **Blocked probe.** No driver errors at all, yet the card still lands tens of seconds late. Look for another device failing enumeration on the same controller (`device descriptor read/64, error -110` → `attempt power cycle` → `unable to enumerate USB device`). `hub_event()` holds the hub's device lock for that entire cycle, and a sibling's card registration needs the same lock — so the card appears in the same second the failing port finally gives up. If those two timestamps are ~1 s apart, that is the whole story.

    Mitigation is limited, and the shape of it matters:
    - **`early_stop` helps.** Per the [kernel ABI docs](https://www.kernel.org/doc/Documentation/ABI/testing/sysfs-bus-usb) it "limits each port to just **two** initialization attempts" — a cap, not an off switch. Measured on one host: cycle 64 s → 43 s, with the audio outage shrinking in lockstep. It is a plain flag and takes no lock, so the write returns immediately.
    - **`disable` does not work from userspace, despite being the documented off switch.** `disable_store` takes the hub device lock — the very lock `hub_event()` holds for the whole cycle. Measured: a unit that started 6 s _before_ the port connected still blocked 50 s in that write, landing 1 s after the storm it was meant to prevent. Running it earlier cannot help, including from initrd, and leaving it in parks a `oneshot` in `sysinit.target` for the duration.
    - **udev cannot target port devices at all** (empty `uevent`, no subsystem, zero `usb_port` entries in the udev database), so any of this takes a systemd oneshot writing sysfs.

    The real fix is below the OS: unplug the offending device, or disable the port in firmware. Check the port's neighbours (`/sys/bus/pci/devices/<ctrl>/usb*/`) before assuming it is external — on a desktop board the block around it is often all internal devices. Do **not** trust `connect_type` to tell you a port is unused; boards mislabel populated ports as `not used`.

- **`pipewire: mod.x11-bell: X11 display (:0) has encountered a fatal I/O error`.** Upstream PipeWire loads `module-x11-bell` in its default `pipewire.conf`; on a Wayland session it grabs a display that Xwayland then tears down. Purely the X11 bell — no effect on audio. Not worth forking the stock `pipewire.conf` to drop one module.

## Accepted — hardware/driver specific

These depend on the physical test machine and will not appear on other hardware:

- **`Bluetooth: hci0: Reading supported features failed (-16)`** + `bluetoothd: Failed to set default system config for hci0` — controller firmware EBUSY during early init. (Confirmed _not_ a hardening conflict: the bluetooth entries in `nm-module-blacklist.conf` are commented out and BT is active.)
- **`usb 1-8: device descriptor read/64, error -110` / `device not accepting address N, error -71` / `usb usb1-port8: unable to enumerate USB device`** — a device or port that fails enumeration on the test machine. Cabling/hardware, not config.
- **`usb 1-7: parse_audio_format_rates_v2v3(): unable to retrieve number of sample rates (clock N)` / `cannot get freq (v2/v3): err -110`** — a USB audio interface whose UAC2 clock descriptors don't answer; ALSA falls back to the advertised rates and the device works.
- **`pinctrl core: failed to create debugfs directory for AMDI0030:00`** — AMD GPIO pinctrl registering before debugfs is mounted.
- **`systemd: Failed to adjust io pressure threshold, ignoring: Device or resource busy`** (user manager) — systemd PSI trigger on a cgroup that isn't accepting one yet.
- **`upowerd: value "-nan" … for property 'percentage'`** / `no valid voltage value … BAT0` — laptop battery firmware reporting quirk.
- **`wpa_supplicant: nl80211: key not allowed`** / `FT: Failed to set PTK` — Wi-Fi 802.11r fast-transition driver quirk.

## Accepted — opt-in batteries (only with `itera.gaming` / `itera.virtualisation`)

- **`kernel: ptrace attach of "…wine…" was attempted by "…/bin/wineserver"`**, preceded by `__report_access: N callbacks suppressed`. nix-mineral's `settings.system.yama` defaults to `"restricted"` → `kernel.yama.ptrace_scope = 3`, which disables `ptrace` outright (and cannot be relaxed without a reboot). Wine's `wineserver` ptraces its own child processes, so every Proton title logs a burst of these. Games launch and run, but in-Wine debugging is unavailable, kernel-adjacent anti-cheats can refuse to start, and the same setting means `gdb`/`strace` cannot attach to anything on the host. This is the hardening working as configured, not a bug — `itera.gaming` emits a warning pointing at it. A host that wants it back sets `nix-mineral.settings.system.yama = "relaxed"` (ptrace_scope 1 — parent may trace its own children, which is exactly what Wine needs), or picks up the `compatibility` preset via `itera.hardening.preset`, which sets that for this reason.
- **`pressure-vessel-wrap: W: "/run/current-system/sw/bin/getent" is unlikely to appear in "/run/host"`**, `W: Unable to determine architecture of provider / ldconfig`, `W: "run/opengl-driver*/share/drirc.d" is unlikely to appear in "/run/host"`. Steam's pressure-vessel container runtime assumes an FHS host and warns about every Nix store path it cannot map. Cosmetic — the container starts and games run.
- **`pv-adverb: W: Container startup will be faster if missing locales are created at OS level`.** pressure-vessel wants pre-generated locales in the container. A startup-latency hint only; generating Steam's full locale set system-wide costs more than it saves.
- **`libvirtd: Client hit max requests limit 5. This may result in keep-alive timeouts. Consider tuning the max_client_requests server parameter`.** virt-manager pipelines more concurrent RPCs than libvirt's stock per-client limit. Self-limiting (requests queue rather than fail); only worth raising via `virtualisation.libvirtd.extraConfig` on a host that actually sees keep-alive drops.
- **`.libvirtd-wrapp: Domain id=N name='…' is tainted: high-privileges`.** libvirt notes that the domain runs with elevated privileges under `qemu:///system` — informational, and inherent to the system-session setup this battery configures.

## Accepted — shutdown / unmount

Only visible on the console during reboot/poweroff (they happen after journald has
flushed, and there is no pstore on the test hardware, so `journalctl -b -1` does not
capture them):

- **`Failed unmounting /etc/machine-id` / `…/etc/ssh/ssh_host_*` / `/home/<user>/.config` etc.** at shutdown. Inherent to the ephemeral-root stack: tmpfs `/` (wiped each boot) → nix-mineral shadow bind-mounts of `/etc`,`/var`,`/home` → `impermanence` file/dir binds from `/persist` on top. Single-file binds that are still held open at shutdown (`/etc/machine-id` by PID 1, the SSH host keys) can't be cleanly unmounted in the best-effort pre-pivot pass, so systemd logs `Failed unmounting …`. systemd then pivots to the shutdown ramfs and lazy-detaches the rest; the reboot completes cleanly (`systemctl is-system-running` → `running`, 0 failed units on the next boot). Cosmetic — not worth destabilizing the tuned impermanence/machine-id/hardening interplay (see `modules/nixos/core/impermanence.nix`) to silence.
